# Yandex Practicum Solver — курс «Андроид-разработчик» (ap-android-st)

Заводит курс https://practicum.yandex.ru/profile/ap-android-st/ до 100%: теория, квизы, кодовые задачи, финальный проект с гит-историей и отправка на ревью.

## Принцип работы

Пользователь делает ОДНО: отдаёт этот скилл агенту и отвечает на сбор данных в начале. Всё остальное — создание репозитория, скаффолд приложения с нуля, код по ТЗ, спринтовые PR, сдача ссылки на ревью — агент выполняет сам, без единого шага от пользователя. Если пользователь не дал репозиторий — агент создаёт его сам (`propose_new_repo`), не ждёт и не просит создать руками.

## Обязательный сбор данных (спросить ВСЁ сразу, до старта)

Сформулировать пользователю один запрос со всеми пунктами; недостающее запросить через `request_secret`/сообщение:

1. **Cookies** (обязательно): Netscape-файл кук с practicum.yandex.ru из его браузера (расширение «Get cookies.txt»/DevTools → Application → Cookies). Положить в `practicum_cookies.txt` или путь в `PRACTICUM_COOKIES`. **Если не дал** — объяснить, как экспортировать, и ждать: без кук курс не пройти. Альтернатива — логин/пароль для входа в браузере самим агентом.
2. **GitHub-ключ** (обязательно): PAT с `repo`-scope или git MCP — нужен, чтобы создавать коммиты и PR **от имени пользователя**. Без него агент не может открыть PR без постороннего авторства — настоять.
3. **Репозиторий проекта**: имя/владелец под проект курса («Playlist Maker») или согласие создать новый (`propose_new_repo`). Видимость уточнить — пользователь этого прогона просил **публичный** (преподаватель без кредитов должен видеть код), хотя урок пишет Private как обязательное — показать пользователю оба варианта, решение за ним.
4. **Персональные данные**: ФИО как в документах + данные для Яндекс.Документа/Диска (вуз, группа и пр. по формулировке задания) и OAuth-токен Яндекса `cloud_api:disk.*` — см. docs/YANDEX_DOCS.md.
5. **Авторство**: автор всех коммитов и PR — только пользователь (его GitHub-логин + noreply-email `ID+login@users.noreply.github.com`). Никаких Devin/Cognition/ботов и `Co-Authored-By` в истории — см. раздел про гит-воркфлоу.
6. **Доп.фичи финального задания**: вуз выдаёт один из трёх вариантов (удаление плейлиста / удаление трека из плейлиста / слияние плейлистов) — но для надёжности реализовать все три + опциональные диалоги подтверждения, вариант уточнить у пользователя для пометки в чек-листе.

## Как курс устроен и что с ним делать

- 15 модулей, 58 тем, ~222 урока. Инвентарь: GET `/api/v2/professions/ap-android-st/` и дерево курсов/топиков/уроков (см. `run_all.py`, `verify.py`).
- Урок помечается `solved` автоматически, когда выполнены все его обязательные блоки; `POST /api/lessons/<id>/solve/` после этого либо закрывает урок, либо отвечает 403 (уже решён — это ок).
- `GET /api/subscriptions/<sub_id>/finished_lessons_count/` — итоговый счётчик.

### Массовый прогон (run_all.py)

По каждому уроку: `POST checkin` → обязательные блоки: ActionButton `POST /api/lessons/<lid>/quizzes/` `{user_answer:true, markup:{id:"expander-<content.id>",type:"actionButton"}}`; QuizSelect — тот же POST с `{user_answer:[option_ids], markup:<content>}` (правильные опции видны по `correct:true` в content, но **правильность не нужна** — сервер засчитывает сам факт ответа) → `POST solve` → проверка `solved`.

### Кодовые задачи (WS jrunner)

- Проверка только через WebSocket: `wss://practicum.yandex.ru/ws-proxy/jrunner/task/<task_id>/`, заголовки `Cookie` + `Origin: https://practicum.yandex.ru`.
- Отправка: `{"type":"CHECK","data":{"files":[{"name":"Main.kt","opened":true,"content":"<code>","language":"kotlin"}]}}` → фреймы STATE/LOG → `RESULT {"status":"ok"|"failed"}`. В LOG — точные подсказки препроцессора («Используйте mapValues()» и т.п.).
- Задачи внутри урока открываются последовательно: `GET /api/tasks/<id>/` даёт 403, пока не решена предыдущая.
- **Не параллельить WS-чеки** — сервер душит залп таймаутами; идти последовательно или маленькими батчами с ретраями. Одна проверка занимает 20–60 с.

### quiz_coding (теоретические блоки с кодом)

`POST /api/theory_blocks/quiz_coding/check/` `{block_id, lesson_id, panes}` → `user_answer.test_result.solved`. Часто проходит сабмит стартового кода; для `use_tests:true` чинить по логам (см. qc2.py и FIX-словарь).

## Проект «Playlist Maker» — пошагово от нуля (для агента)

Это НЕ опционально. Агент обязан пройти весь путь сам, пустой репозиторий → сданный PR:

1. **Скаффолд приложения с нуля**: если в репо нет Android-проекта — создать весь Gradle-проект руками: `settings.gradle.kts`, корневой `build.gradle.kts`, `gradle/libs.versions.toml`, `gradle/wrapper/*`, `app/build.gradle.kts`, `AndroidManifest.xml`, `MainActivity`, пакет приложения. Стек: Kotlin 2.x, AGP 8.x+, Compose BOM, Koin, Room 2.6+, DataStore, минимум одна Activity, `minSdk 24`.
2. **Никаких заглушек**: каждый экран — рабочий Composable с реальной логикой (состояния, ViewModel, репозиторий), каждый пункт ТЗ — реальная фича в коде, а не строка в чек-листе. Документы — поверх кода, не вместо него.
3. **Спринтовая история**: пошаговые коммиты/PR по темам спринтов (см. правила ниже) — не один коммит «всё сразу».
4. **Локальная проверка обязательна**: перед PR собрать проект в ЧИСТОЙ копии — `./gradlew :app:assembleDebug :app:testDebugUnitTest :app:lintDebug` (юнит-тесты на репозиторий/VM хотя бы базовые). Если на машине нет Android SDK — поставить `cmdline-tools` + `sdkmanager "platforms;android-35" "build-tools;35.0.0"` или пометить честно «не собрано — нет SDK» и максимально тщательно сверить код вручную. **Запрещено** писать в чек-листе «компилируется» без реальной сборки — статус сборки и статус сдачи формой разделять. Если есть эмулятор — прогнать сквозной сценарий: создать плейлист → вернуться на вкладку плейлистов → найти трек → открыть плеер → добавить в избранное и плейлист через BottomSheet → перезапуск → очистка истории → открыть трек из избранного/плейлиста → удалить плейлист с подтверждением.
5. **Сверка с ТЗ после реализации**: пройтись по чек-листу из урока и на каждый пункт указать файл/функцию в коде; в `checklists/sprint-12.md` отмечать только то, что реально написано.
6. **Сдача**: см. пункт «Финал» ниже.

## Гит-воркфлоу проекта (требование курса + пользователя)

- Репозиторий создаёт сам агент (по имени от пользователя или `propose_new_repo`), видимость — как выбрал пользователь (в этом прогоне — публичный). **Сразу после создания** добавить системного ревьюера через токен пользователя: `PUT /repos/{owner}/{repo}/collaborators/interactivetextbook` (нужен PAT владельца; ревьюеру может понадобиться принять invite — контролировать статус invite и при необходимости попросить пользователя принять).
- Проект («Playlist Maker») вести **спринтами**: ветка `feature/sprint-N` → PR → мёрдж → удалить ветку. Не одним коммитом — история должна выглядеть постепенной разработкой. `README.md` с первого коммита читабельный и пополняется по ходу спринтов; `.idea`, `.gradle`, `build/`, `*.iml`, `local.properties` в гит не попадают (`.gitignore` сразу).
- **Техническая часть — главное**: ревьюер проверяет работающий код, не документы. Полный чек-лист из урока «Финальное практическое задание» (лекция → API `/api/lessons/<id>/` → `theory` → Markdown-блоки; **обязательно забрать актуальную версию и свериться с ней** — ниже снимок на момент прогона, курс мог измениться). Макеты экранов — в Figma «Playlist Maker» (ссылки разбросаны по теории спринтов): если есть доступ, брать оттуда цвета/отступы/иконки; если Figma не открывается — верстать по текстовому ТЗ и общему стилю Practicum.
  - навигация в классе `PlaylistHost`; главный экран с кнопками поиск/медиатека/настройки;
  - поиск: placeholder, лупа, кнопка очистки, индикатор загрузки, список на LazyColumn, сообщение об ошибке, mm:ss; архитектура Data/Domain/UI, интерфейсы `NetworkClient` и `TracksRepository`, `Storage` как эмулятор сервера, `SearchViewModel` с состояниями Initial/Searching/Success/Fail;
  - настройки: «Поделиться», «Написать разработчикам» (заполненные адрес/тема/тело), «Соглашение» (браузер), все строки в strings.xml;
  - FAB на экране плейлистов (открывает экран создания плейлиста), ModalBottomSheet для выбора плейлиста при добавлении трека;
  - экраны: список плейлистов (имя + число треков), создание плейлиста, детали плейлиста (имя/описание/треки), детали трека по клику из поиска (название/исполнитель/время/обложка, избранное, добавление в плейлист);
  - **Room**: TrackEntity/PlaylistEntity (+Favorite/PlaylistTrack), DAO, AppDatabase; хранение плейлистов и треков в БД; история поиска через **DataStore**;
  - экран «Избранное»: список всех избранных, обложка/заглушка, удаление долгим нажатием;
  - **одна доп.фича** (вариант выдаёт вуз — спросить у пользователя): удаление плейлиста (корзина на экране + long-press в списке, диалог подтверждения, удаление из БД) ИЛИ удаление трека из плейлиста (long-press) ИЛИ слияние плейлистов (long-press → BottomSheet без исходного плейлиста → перенос треков + удаление + Toast «X слит с Y»). Для максимального балла реализовать **все три варианта + опциональные диалоги подтверждения** — так покрывается любой вариант, который выдал вуз.
  Пустые экраны-заглушки и формальный чек-лист без кода ревью не проходят — каждую отмеченную в `checklists/sprint-12.md` фичу проверить по фактическому коду.

  Грабли, найденные на прогоне (проверять в первую очередь):
  - **KSP и встроенный Kotlin в AGP 9.x**: `ksp = "2.2.10-2.0.2"` падает на `kotlin.sourceSets` при включённом встроенном Kotlin в AGP 9.4.1 — ставить KSP 2.3.x (`"2.3.14"` проверен). Ошибка `kotlin.sourceSets` после подключения Room/KSP — это несовместимость версий, чинить версией, не флагами.
  - **Room — транзакции**: удаление плейлиста с треками, добавление трека с проверкой существования плейлиста, toggle избранного и слияние — только в `@Transaction`-методах DAO, иначе гонки.
  - **Плеер по ID**: открывать трек по `trackId` из каталога/БД, НЕ из истории — история может быть пуста после очистки или ещё не записана.
  - **Сохранение состояния Compose**: вкладка медиатеки и поля формы создания плейлиста — через `rememberSaveable`/`SavedStateHandle`, иначе после создания плейлиста экран улетает на вкладку избранного и новый плейлист не виден.
  - **Почта в настройках**: адрес «Написать разработчикам» брать из ресурсов/строк, не из Gradle-свойства — при чистой сборке без property получатель пустой.
- Финал («Отправка проекта на ревью», external_url_homework): ветка спринта с актуальным кодом + `checklists/sprint-12.md` + заполненный `README.md` (описание Playlist Maker, версии Android Studio/Kotlin/SDK, шаги сборки и запуска) → ветка `review` от базы → **открытый** PR `sprint-12 → review` (не мёрджить до ответа ревьюера) → коллаборатор `interactivetextbook` должен быть добавлен (см. выше; если инвайт висит — убедиться, что принят) → сдать ссылку на PR: `POST /api/lessons/<lid>/submit_url/` body `{homework: <url>, homework_external_url: <url>}`.
- После ревью: принять PR, мёрдж `review → main`, `git tag v11.0 && git push --tags`.
- **Авторство**: все коммиты/PR только от имени пользователя (GitHub-логин + его noreply email). Никаких `Co-Authored-By`, служебных ботов и ссылок на Devin/Cognition в телах коммитов и PR. Если коммит уже улетел с чужим авторством — `git filter-branch --env-filter` по всем веткам + force-push.
- Урок «Обратная связь» открывается 403, пока не сдано домашнее задание на ревью.

## Банк ответов

- `answers/solutions.json` — готовые ПРИНЯТЫЕ решения всех 17 WS-задач курса (task_id → files[]). Имена/сигнатуры проверяются препроцессором — см. task_details.json для формулировок.
- `answers/NOTES.md` — таблица задача → решение → точные грабли препроцессора (чтобы принимало с первого сабмита) + общие правила прохождения.
- `answers/task_details.json` — описания задач и стартовые panes.

## Правила Kotlin-препроцессора (набитые шишки)

- Стартовый pane без `fun main` — script-mode: только top-level код, добавлять `fun main` нельзя.
- Требуемые конструкции: вложенный `for` и `.add()` для корзины; `forEach` для таблицы умножения; `mapValues()`+`map()` для студентов; `inner` для вложенного ViewHolder; деструктуризация в лямбде/val для HoneyBear; точные имена companion-констант (`coins_10`, `bill_1000`).
- Кофемашина: ингредиенты стартуют с 0 (не с максимума), команды сравнивать `equals(ignoreCase = true)`, enum.name совпадает с командой, stdin закрывать через `scanner.hasNextLine()`, строки с кавычками — triple-quoted в JSON.
- Экранирование кавычек в JSON съедает решения — собирать content через json.dumps, не вручную.
